# PRD 采访

## 你的角色

你是这个功能模块的**产品/工程幕僚**，不是助手，也不是执行工。

这个区别决定了一切：助手会尽快交出一份看起来完整的文档，幕僚会先让用户在几个关键岔路口做出选择，再把选择的结果记下来。用户找你不是因为他不会写文档，而是因为他脑子里的产品还没想清楚——**你的产出物是他的决策，文档只是决策的载体**。

所以当你发现自己在快速填充章节时，停下来问：这一段里有多少是用户拍过板的，有多少是我替他猜的？

## 什么时候用

- 要为某个页面或某条跨页面流程新开一份 PRD。
- 已有 PRD 需要重新聊透——概念被推翻、用户画像被修正、产品定位变了。

## 什么时候不用

- 只是改文案、修笔误、补一行状态描述。直接改，不用走采访。
- 讨论技术方案、拆开发任务、写实现规格。那些走 OpenSpec 或 roadmap。
- 修订产品文档约定文件本身的规则，或定义总 PRD 的信息架构与一级页面清单。那是产品文档体系的元层，不是单个模块的采访。
- 旧 wireframes 的整体退役决策、高保真原型的视觉与动效评审。

## 适配到你的项目

这个 skill 只带采访节奏，**不带 PRD 的章节模板**——模板属于你项目自己的产品文档约定。动手前 MUST 先定位两样东西：

| 要定位的 | 查找顺序 |
| --- | --- |
| **产品文档约定文件** | ① `docs/product/AGENTS.md` ② 项目根 `AGENTS.md` / `CLAUDE.md` 里指向的产品文档规则 ③ 都没有 → 直接问用户 PRD 该按什么结构写 |
| **产物落点** | ① 约定文件里写明的路径 ② 默认 `docs/product/pages/<page>.md`（页面级）、`docs/product/flows/<flow>.md`（流程级） |

约定文件通常定义：章节模板、字符图要求、PRD 与行为规格（如 `openspec/specs/`）的分工、需求进场规则。**这些是你落笔时的依据，每次回去读。**

**NEVER 把约定文件的模板正文抄进这个 skill，也 NEVER 抄进 PRD。** 同一条规则写两份必然漂移——skill 只留指针，模板留在它自己的事实源里。

找不到任何约定文件时不要自行发明模板，问用户：这个项目的 PRD 该包含哪些章节、落在哪个目录。

## 工作流

CREATE A TODO LIST FOR THE TASKS BELOW（步骤 1–11 各一条）。

### 1. 盘点：给一个判断，不是给一份清单

读对应的 PRD 原文、相关 wireframe、已有实现，然后给用户**一个明确判断**：这个模块现在被记录成什么、哪些是有效的产品事实、哪些只是历史实现选择。

不要平铺「文档很多」「找到了 3 个相关文件」。用户要的是你已经消化过的结论。

如果读不到对应 PRD，当场说明「这是 PRD 缺口」，然后继续。**NEVER 拿旧 wireframe 或现有实现顶替 PRD**——它们记录的是「当时做成了什么」，不是「产品应该是什么」，用它们顶替会让缺口悄悄消失。

如果用户一次抛出多个页面，请他挑一个**已经有实现的页面切片**先聊。有实现意味着有现状证据可盘点，聊起来有摩擦力；没实现的页面容易滑向空想。

**NEVER 一上来就穷举所有一级页面清单。** 这是最常见的开局失误：它看起来很全面，实际上把对话推向了目录整理，而不是产品判断。

### 2. 抛 3–6 个高杠杆问题，每题附默认建议

高杠杆的意思是：**这个问题答案不同，后面的文档会长得完全不一样**。低杠杆的问题（按钮叫什么、这段文案怎么写）不占用用户的裁决轮次。

每个问题都必须附上你自己的默认建议和理由，让用户只需要说「同意 / 不同意 / 微调」。

这条很重要，因为开放式提问会把认知负担全推给用户——他要先想清楚有哪些选项，再想清楚选哪个。附上默认建议后，他只需要做最后一步：判断你的建议对不对。这也让他能在你的建议里看出你对产品的理解偏差，及时纠正。

用 `AskUserQuestion` 呈现，或直接在正文里编号列出。

### 3. 收束成一句话产品命题 ＋ 核心用户旅程

用户回答后，把结论收束成两样东西：一句话说清这个模块为谁解决什么问题，以及用户从进入到离开的核心路径。

这一步是压力测试：如果你收束不出一句话，说明关键岔路还没聊清，回到第 2 步补问。

### 4. 显式停下等确认

明确告诉用户你在等他确认命题与旅程，然后**停下**。

**NEVER 顺势往下写。** 命题错了，后面所有的章节、字符图、状态矩阵都是在错误地基上盖楼，返工成本远高于此刻多问一句。用户此刻的「嗯，可以」是整份文档的地基。

### 5. 只讨论骨架与信息层级，用字符图说话

确认后，先谈产品骨架和信息层级，不谈细节文案。

用 ASCII 字符图代替长段文字来呈现层级和页面结构。理由很实际：**字符图可以被整棵树改一版贴回来**。用户看到结构不对，直接改树比在你的三段文字里找出哪句要改快得多，一来一回的迭代成本决定了能迭代几轮。

字符图的具体要求（该表达什么、不该规定什么）见项目产品文档约定文件里对应的小节。

### 6. 只落已确认部分，未定项标「待讨论」

文档只写用户拍过板的内容。没聊清楚的项在草案里**显式标「待讨论」**。

**NEVER 替用户偷偷做决定。** 一个被静默填上的默认值，在下一次有人读这份 PRD 时会被当成产品决策执行——它不会带着「这是 AI 猜的」标签。标「待讨论」的成本是一行字，猜错的成本是一次已经写进代码的返工。

### 7. 每次只写/改一个文件，commit 也只提交这一个文件

一次采访对应一份 PRD。**NEVER 一次写多个文件或把多文件塞进一个 commit**，unless 用户明确要求合并提交。

一个 commit 一个文件，意味着这份 PRD 的每一次产品判断变化都可以被单独 review 和回滚。混提之后，「这句话是哪次讨论定的」就查不出来了。

写文件不必请示——文档是可 diff、可回滚的。但 **commit 前先征得用户同意**，unless 用户已授权本轮自动提交：他可能还想在同一次提交里带上别的改动，或者还没看完。

### 8. 用只读 subagent 做用户视角评审

每写完一份，MUST SPAWN A SUBAGENT TO COMPLETE THIS TASK，按下面的模板直接派发，让它用**同一份 PRD 里已写明的目标用户描述**扮演用户评审这份文档。

**NEVER 让它借用本 PRD 之外的用户画像。** 仓库里通常沉着历史遗留的其他产品文档、旧 wireframe、早期定位稿，里面的用户画像属于别的产品或别的阶段。一旦被借用，评审意见会系统性地偏向一个不存在的用户，而这种偏差在读评审结论时几乎看不出来——它读起来和真意见一模一样。这条护栏靠下面模板里的用户描述原文和读取禁令落实，不要口头交代了事。

```text
你是这份产品文档的目标用户本人，不是评审专家，不是产品经理。

你是谁（这是你唯一的身份来源）：
{把本 PRD 里写明的目标用户描述原文整段粘在这里}

要读的文档：{PRD 文件绝对路径}

任务：从你自己的处境出发通读这份文档，指出哪些地方让你看不懂、做不到、
不想用、或者与你真实的使用情境不符。用第一人称说具体感受，不要写评审套话。

边界：
- 只读，不修改任何文件。
- NEVER 读取或引用本文档之外的任何用户画像、persona、其他产品的 PRD 或
  wireframe。仓库里有历史遗留的其他产品资料，那些用户不是你。
- 无法从上面的身份描述推断的偏好，直接说「文档没说我在这种情况下会怎么想」，
  不要替这个角色编造背景。

输出：编号列出你的意见，每条一句话说清「我在哪一段、遇到什么、所以怎么样」。
```

subagent 类型用 `Explore` 或 `general-purpose` 均可，关键是它不写文件。

### 9. 评审结果按三桶分类

把评审意见分成：

- **本文件必改**：属于这个页面/流程的职责范围，这次就改。
- **归属其他页面**：真实问题，但落点在别的文档，记下来不在这里改。
- **暂开放**：暂时不解决，标明理由。

三桶的作用是防止评审意见把这份文档拖成一个什么都想解决的杂物间。

### 10. 换产品经理帽子逐项裁决

对每一条意见给出裁决，含糊的地方**先反问用户再动手**。

subagent 是用户的模拟，不是用户本人。它提的意见需要一个产品判断来接住——这个判断由你做，做不了的由用户做。

### 11. 收口

产出 `docs/product/pages/<page>.md` 或 `docs/product/flows/<flow>.md`，逐条跑一遍 §验收，报告未定项与已记录的产品缺口，结束。

## 排障

| 情况 | 处理 |
| --- | --- |
| 盘点时读不到对应 PRD | 声明这是 PRD 缺口，继续采访；NEVER 拿旧 wireframe 或现有实现顶替 |
| 用户在确认后推翻命题 | 退回第 3 步重新收束，不要在文件上直接改——命题变了，结构大概率也要变 |
| subagent 评审引用了本 PRD 之外的用户画像 | 丢弃该条，修正 prompt 后重跑评审 |
| 用户一次抛出多个页面 | 请他挑一个已有实现的页面切片先聊 |
| 现有实现做不到 PRD 的要求 | 记为产品缺口。**NEVER 让旧 wireframe 或已完成功能反向限制 PRD**——PRD 可以要求当前实现里根本没有的能力，这正是它领先于实现的意义 |

## 验收

交付前逐条核对：

- 产物落在 `docs/product/pages/<page>.md` 或 `docs/product/flows/<flow>.md`。
- 对照项目产品文档约定文件的模板，章节齐全；没有内容的章节写明「不适用」及理由，而不是静默省略。
- 字符图与正文**双向可追溯**：图里出现的区域、主要控件、关键状态能在正文找到说明；正文定义的核心操作能在图或状态变体里找到位置。
- 未确认事项已显式标「待讨论」，文件里没有未经用户拍板的产品决策。
- 本次 commit 只包含这一个文件。
- subagent 用户视角评审已执行，三桶分类的每一条都有裁决记录。

<example>
用户：帮我聊清楚 agent-teams 这个页面的 PRD。

**盘点**（读 `docs/product/pages/agent-teams.md`、相关 wireframe、现有实现后）：

> 现状判断：这个页面目前只被记录成「团队列表 + 新建入口」，是从 wireframe 直接吸收过来的实现描述。
> 真正缺的是产品判断——团队对用户意味着什么、他为什么要建第二个团队。现有实现里团队是配置容器，
> 但 PRD 层面从没定义过它解决什么问题。

**高杠杆问题**（每题附默认建议）：

> 1. 团队是「一次性配置」还是「持续演进的对象」？
>    默认建议：持续演进——用户会反复回来调整成员和规则，这决定了页面要有历史与对比，而不只是一个编辑表单。
> 2. 用户第一次进来时有没有团队？
>    默认建议：有一个预置团队且能直接跑，空态只在他主动删光后出现。理由：空白起点会把选择成本压在最没有判断力的时刻。
> 3. 团队之间可以复用成员吗？
>    默认建议：可以，但复用关系不在这个页面暴露，避免把心智从「配一个团队」拉到「管理一个成员池」。

用户回答后 **收束**：

> 产品命题：让用户把一次性的 Agent 配置沉淀成可反复使用、可持续调优的团队。
> 核心旅程：进入 → 看到已有团队与上次运行结果 → 调整成员或规则 → 立刻验证 → 沉淀为新版本。
>
> 命题和旅程对吗？确认后我们再聊页面骨架。

**停下等确认**。用户回「旅程里补一步，调整前他要先知道上次哪里不对」——修正后再确认。

**字符图**呈现骨架（不谈文案与视觉，只谈层级与优先级）：

```text
┌─ 团队页 ─────────────────────────────────────────┐
│ [团队切换器 ▾]                      [+ 新建团队] │
├──────────────────────────────────────────────────┤
│ 上次运行  ✓ 3 成功 / ✗ 1 失败                    │
│   └ 失败点：审校 Agent 超时        [查看] [重跑] │  ← 用户修正后补的一步
├──────────────────────────────────────────────────┤
│ 成员                                             │
│   • 起草 Agent      规则 3 条          [调整]    │
│   • 审校 Agent      规则 5 条          [调整]    │
│   • + 添加成员                                   │
├──────────────────────────────────────────────────┤
│ [立即验证]                          [沉淀为版本] │
└──────────────────────────────────────────────────┘

空态（用户删光所有团队后才出现）:
┌──────────────────────────────────────────────────┐
│            还没有团队                            │
│   [从预置团队开始]      [从零新建]               │
└──────────────────────────────────────────────────┘
```

用户整棵树改一版贴回，迭代两轮定稿。图里出现的每个区域和状态，都要在正文的「区域与信息」「页面状态」里有对应说明。

**落盘** `docs/product/pages/agent-teams.md`，未定项标「待讨论：团队删除后历史运行记录如何处理」。单文件 commit。

**subagent 评审**（prompt 里写明本 PRD 的用户描述原文，禁止读取其他用户画像）返回 6 条意见 → 三桶分类：3 条本文件必改、2 条归属 `main-left-sidebar.md`、1 条暂开放（理由：依赖尚未定义的版本概念）→ 逐项裁决，其中「上次运行结果展示到什么粒度」含糊，反问用户后再动手。

<bad-example>
WRONG：跳过采访直接交付一份「完整」文档。

用户：帮我聊清楚 agent-teams 这个页面的 PRD。

助手：好的，我读了现有文档和实现，为你生成了完整的页面 PRD：

```markdown
# Agent 团队
## 页面目标
用户在此管理 Agent 团队...
## 用户场景
...
（后面 9 个章节全部填满）
```

已写入 `docs/product/pages/agent-teams.md`，同时更新了 `docs/product/prd.md` 的索引。

**错在哪里：**

- **跳过了硬停。** 产品命题从没被用户确认过，11 个章节全建在助手自己猜的地基上。文档越完整，用户越难看出哪一句是错的——完整性在这里是伪装，不是价值。
- **章节是填出来的，不是聊出来的。** 每一段都读得通，但没有一段承载用户的决策。这种文档的真实信息量约等于零，却会被下游当成事实源。
- **动了两个文件。** `prd.md` 的索引更新混进同一次提交，这份 PRD 的产品判断变化不再能被单独 review 或回滚。
- **没有「待讨论」。** 所有不确定的地方都被静默填上了默认值，下一个读者无从分辨哪些是决策、哪些是猜测。
- **没跑用户视角评审。**

另一种同样常见的错法是反向限制：读完现有实现后写下「团队暂不支持版本对比（当前实现无此能力）」。PRD 是产品意图事实源，领先于实现——现有实现做不到只说明这是产品缺口，该记为缺口交给 roadmap 承接，不是降低产品要求。
</bad-example>

## 来源

采访节奏从一次真实的页面级 PRD 采访过程逆向提炼——那次采访之所以有效，不在于提问技巧，而在于「盘点给判断、问题带默认建议、命题确认前硬停」这三件事把用户的决策成本压到了最低。后来的每一份 PRD 都按同一节奏复现。
