# Privy 文档 MCP

把 Privy 官方公开文档当作事实源，再和项目里实际安装的 SDK 与架构边界对齐。

## 什么时候用它

**查询 Privy 文档**

我需要登录、嵌入钱包、充值、策略、webhook 或迁移的当前官方说法，想要带精确链接的证据，而不是凭记忆猜 API。

**实现登录接入**

我在改 Privy 集成，想让 skill 先读项目、整理证据表，再做最小且安全的代码改动。

**核对钱包策略**

我已经有代码或架构判断，想和 Privy 官方文档交叉验证，同时不暴露密钥或私有用户数据。

**不接**

不处理与 Privy 无关的通用区块链方案、Privy 后台管理、生产密钥操作或私有支持问题。MCP 只当公开文档来源使用。

## 它会产出什么 / 你会看到什么

**文档证据不等于运行时验证。** 这个 skill 会先区分官方说法、项目约束和推断，再决定是否改代码。

- **证据包**：输出 `PRIVY_EVIDENCE_PACKET`，包含问题、项目上下文、引用链接、冲突与未验证项。
- **文档查询**：优先用运行时已有 MCP；不可用时改用内置只读客户端或官方静态文档。
- **实现改动**：只改用户和项目规则允许的文件，保留密钥、服务端信任边界和失败关闭行为。
- **验证命令**：实现类任务会按项目顺序跑测试、类型检查、lint、build 或其他确定性检查。
- **绝不会做**：调用反馈写入工具、把密钥发进 MCP 查询、擅自改编辑器 MCP 配置、声称能访问 Privy 后台。

## 前置条件 / 边界

**前置**

需要一个明确问题或项目路径，并能读取公开 Privy 文档；实现类任务还需要足够项目上下文来识别已安装包和信任边界。

**相邻工作**

| 需求 | 交给 |
|---|---|
| 与 Privy 无关的钱包架构 | 区块链架构流程 |
| Privy 后台操作或密钥轮换 | 人工运维流程 |
| 生产事故支持 | 项目值班流程 |

**硬边界**

- 公开 App ID 配置和私有 App Secret 处理必须分开。
- MCP 查询必须最小化并脱敏。
- 官方示例不能悄悄覆盖项目已经接受的架构边界。
- 文档与本地类型定义冲突时，报告冲突，不强行选择其一。
