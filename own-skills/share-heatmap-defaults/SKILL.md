# 占比热力图默认判断

## 触发条件

- 用户要求为某个领域/数据集做"热力图"。
- 描述里同时出现占比/分布/份额/谁大谁小/谁占多少这类语义词（或明显在问"谁占大头""各项各占多少"）。

## 不触发（Do NOT trigger）

- 描述里没有占比/份额语义，格子大小本身没有业务含义——比如"每天一个格子、颜色代表当天活跃度"的日历热力图，或行列交叉格子代表相关性的相关矩阵热力图。这类场景格子大小不该跟着数值变化，维持传统色块深浅热力图才是对的。
- 用户是在柱状图/饼图/折线图等完全不同的图表类型之间做初选，不是"热力图内部该怎么编码"的问题。
- 用户要的是 Treemap 具体怎么实现（布局算法、坐标计算、CSS 写法、验证脚本）——这些不属于本判断范围，交给模型按经验正常处理。

## 工作流

1. 检查描述里有没有占比/分布/份额语义词。没有 → 不适用本 skill，按常规热力图（颜色深浅、格子大小固定）处理。
2. 有的话，问自己一句：**这些格子/方块的"大小"本身有没有业务含义？**
   - 有（大小本身代表占比/份额）→ 默认选 **Treemap**：方块面积按数值真实比例切割，颜色只能做辅助维度，NEVER 用颜色代替面积表达占比大小。
   - 没有 → MUST 维持传统色块深浅热力图，NEVER 不分青红皂白都套用 Treemap。
   - 拿不准（信号模糊、两种解读都说得通）→ 跳转到下方「失败路径」，直接问用户澄清，不要凭第一直觉选一个。
3. 如果同一份数据横跨多个统计口径（比如累计、近 24 小时、近 1 周、近 1 月、近 1 年），NEVER 把"面积用口径 A、颜色用口径 B"当默认设计——这是同一类盲区的变体，看起来信息更丰富，实际会让人分不清两种视觉编码分别代表什么。默认做法是加一组切换控件（Tab/下拉都可以），切换时让**面积和颜色同时**按被选中的那一个口径重新计算。
4. 【容易漏想】如果用户要求的多个口径里，某个口径在参与比较的实体上覆盖率明显偏低（比如只有一半项目查得到这项数据），NEVER 为了让几个切换按钮"看起来对等"就编造缺失数值，也不要放任大片格子因为没有数值而空着/消失——两种处理在读者眼里都像是图表渲染出了 bug，而不是"这个口径本来就没数据"。正确做法：把这个口径整个从切换控件里拿掉，换成图表之外的一段说明或一张小表格，并写清楚为什么没做成 Treemap（数据源覆盖不到、口径不可比等）。这一步很容易漏想，因为"三个口径都做成对称的切换按钮"看起来是更工整的默认设计，但工整不能建立在编数据或留空洞之上。
5. 【容易漏想】如果参与比较的实体天然分属体量差异悬殊的不同类别（比如把"巨头级别的项目"和"某个巨头旗下的子项目/衍生品"放进同一张图比总量，巨头所在类别会把其他类别的所有项目一起挤成看不清的碎屑），NEVER 指望"把小项目折进一个「其他」聚合块"就能解决——那能救的是"类别内部的长尾"，救不了"类别之间的量级差"。默认应该按类别拆成多张独立的小 Treemap，每张只在类别内部计算占比，类别与类别之间不做面积可比（跨类别的体量对比通常也不是用户真正想看的信息）。
6. 产出后自检一句话：**只看方块的面积大小，能不能看出谁占比更高？** 如果答案是"看不出来，得看颜色深浅才能判断"，说明编码方式选错了，回到第 2 步重新判断。

完成以上步骤后，产出一个明确的编码判断结论（Treemap / 传统网格；是否需要口径切换控件；是否需要按类别拆图），带着这个结论再开始动手实现，不要先做一版凭直觉的默认实现，等用户来纠正。

## 失败路径

- 如果占比语义信号模糊（比如只说"做个热力图看看各板块表现"，不确定"表现"是不是"占比"），不要擅自假设，直接问用户一句"这个热力图是要看各项占整体的比例，还是看每一项自己的强弱/活跃度？"——前者走 Treemap，后者走传统色块网格。
- 如果触发词是"分布"但语境更像"数值随某个维度怎么疏密变化"（比如"用户年龄分布热力图""访问时段分布热力图"），先确认这是"谁占整体多少份额"还是"数值在某个维度上怎么疏密分布"——前者走 Treemap，后者可能是直方图/密度图，都不归本判断管，需要先问清楚。
- 如果格子大小的业务含义本身有争议（比如既有"每个分类占比"又有"每个分类自己的活跃度"两种解读），同样问清楚再动手，不要凭第一直觉埋头实现。

## Treemap 实现默认用 ECharts，以及几个真踩过的坑

编码判断（选 Treemap）之后，具体怎么落地本来不归本 skill 管，但下面这几条是实际做过程中真正踩过的坑，值得单独记下来——不是"怎么写布局算法"这种通用实现细节，而是"选了 ECharts 之后，它的默认行为会在没人提醒的情况下直接产出一张看起来像渲染出 bug 的图"：

- **默认工具**：Treemap 优先用 Apache ECharts 的 `series.type: 'treemap'`，不要自己手写 squarify 布局——自己写的布局算法很容易漏掉"面积够大但形状被拉成细长条"这类边界情况。Artifact 之类有 CSP 限制、不能挂外部 CDN 的环境，把 echarts.min.js 整份源码下载下来内联进 HTML 里（体积大约 1MB，用 `curl` 下载后拼进 `<script>` 标签，不要用会做内容摘要/转述的抓取工具去拿这个文件，会把代码内容摘坏）。
- **颜色坑**：ECharts 的 treemap 默认按子节点顺序自动分配调色板颜色，不会自动套用你想要的板块主色——同一个板块（比如同一个类别）里的每个项目会被配上完全不同的颜色，看起来像是"每个项目自己一个颜色"而不是"这个板块统一一个颜色，靠面积区分项目"。必须显式设置 `series.color: [你的单一颜色]` 并配合 `colorMappingBy: 'index'`，才能让整个板块用同一色系、只靠明暗/面积区分层级。
- **leafDepth 坑（下钻出来是空的）**：用 `leafDepth` 限制初始只显示一层、配合 `nodeClick: 'zoomToNode'` 点击下钻，是 ECharts 官方文档给的标准下钻方案，但 `leafDepth` 是相对"最初的根节点"计算的，不是相对"当前缩放到的节点"——所以点进一个带 `children` 的聚合节点（比如"其他 N 项"）之后，它的子节点因为深度超过 `leafDepth` 依然被判定为该隐藏，下钻的结果是一片空白，很容易被误判成"点击事件没生效"。稳妥的做法是不用 `leafDepth`/`nodeClick` 这套官方机制，自己在 JS 里维护"当前展示的是哪一层数据"的状态（一个简单的 drillState），点击聚合节点时用 `setOption` 直接换成一批扁平数据重新渲染，退出下钻同理换回原数据——布局和动画依然交给 ECharts，只是不依赖它自己的层级下钻状态。
- **"顶部/角落有些看起来像没画完的白色方块"这个症状，对应的原因**：如果不设置 `leafDepth` 就直接把 `children` 塞进 `data`（想用父子结构表示"聚合块可以展开看明细"），ECharts 默认会把子节点在父节点的矩形区域内直接摊开铺满，而不是先收起成一个代表父节点的方块、等点击才展开。子节点数值一旦很小，摊开后每个子块只有几像素宽，块与块之间的分隔边框（通常用背景色/表面色）几乎吃掉全部可见面积，视觉上就是一排"空白/白色的碎块"。看到这个症状时，根源通常不是渲染管线出了故障，而是数据结构选错了——不该指望嵌套 `children` 自动帮你收起聚合节点，要么显式做小值折叠（面积/宽高低于阈值的项目合并成一个不带 `children` 的扁平聚合节点，明细放进 tooltip 或者配合上面的 drillState 方案做下钻），要么干脆不做聚合，允许小项目各自占很小的面积。

## 不管的范围

以下仍然不属于本判断的范围，交给模型按经验正常处理：
- 不用 ECharts、自己手写布局算法时的坐标计算细节。
- 怎么写脚本验证布局算法本身对不对。
- 配色方案、色阶选取（选好"用单一色系"之后，具体色值怎么取不归这里管）。
- 数据从哪抓、抓多准。

## Examples

<example>
用户: "帮我看几个业务线的营收占比，出一个热力图。"

判断: 描述里有"占比" → 触发本判断。方块大小本身有业务含义（代表营收占比）→ 默认选 Treemap，方块面积按各业务线营收比例切割，颜色可以叠加同比增速之类的辅助维度。不需要先做一版均匀网格再等用户纠正。
</example>

<example>
用户: "帮我做一个过去一年每天的网站访问量热力图，像 GitHub 的贡献图那样。"

判断: 描述里没有"占比/份额"语义，是"每天一个格子、颜色代表当天访问量"——格子大小（每天）本身没有业务含义，只有颜色代表数值。默认走传统色块深浅热力图（日历网格），不套用 Treemap。
</example>

<example>
用户: "各个渠道获客成本占比，再加一个能切累计和最近一周的热力图。"

判断: 有"占比"语义 → 选 Treemap。同时数据横跨"累计"和"最近一周"两个口径 → 加切换控件，切换时面积和颜色同时按选中口径重新计算，不要把面积固定绑累计、颜色固定绑最近一周。
</example>

<example>
用户: "把这几大类项目（体量差好几个数量级）的市场份额做成 Treemap，按营收/交易量/用户数切换着看，用户数这个口径好多项目查不到。"

判断: 有"份额"语义 → 选 Treemap。但两个连带问题要先处理：① 类别之间体量差好几个数量级 → 不塞进一张图，按类别拆成多张独立小 Treemap，面积只在类别内部比较；② "用户数"口径覆盖率明显不齐 → 不硬凑成第三个切换视图（会导致编数据或大片留空），改成图表外的一段说明或小表格，写清楚为什么没做进 Treemap。
</example>

<bad-example>
WRONG: 用户说"看看各个渠道获客成本占比"，模型直接做了一个所有方块大小相同、只靠颜色深浅区分成本高低的网格热力图，等用户说"不对，我要 Treemap"才回头重做。

Reason: 描述里已经出现"占比"这个明确信号，判断动作应该在动手前完成，不是等用户纠正后才切换编码方式。整层渲染逻辑（布局方式、坐标定位、配色映射）都要推倒重来，属于本可避免的返工。
</bad-example>

<bad-example>
WRONG: 用户说"做一个近一年每天交易笔数的热力图"，模型因为看到"热力图"三个字，直接套用 Treemap，把 365 天做成 365 个大小不一的方块。

Reason: 这个场景里"天"是固定网格维度，格子大小没有业务含义，只有颜色该变化。不分青红皂白地把所有"热力图"请求都套 Treemap，和不分青红皂白全用均匀网格是同一种错误的两个方向，本 skill 要防的是判断缺失，不是把默认值从一个极端换成另一个极端。
</bad-example>

<bad-example>
WRONG: 模型把体量相差几十倍的两类东西（比如"行业里的巨头公司"和"某个巨头旗下的一条子业务线"）画进同一张 Treemap，结果其中一类的所有项目全部被挤成几像素宽的碎屑；模型试图用"把小项目折进一个「其他」聚合块"来补救，但收效甚微。

Reason: "折进其他"解决的是同一类别内部的长尾小项目，解决不了"整个类别"相对其他类别就小这个问题——问题出在比较的对象选错了层级，不是长尾没收纳干净。应该先按类别拆图，而不是在同一比例尺里硬凑，再指望后期收纳补救。
</bad-example>

<bad-example>
WRONG: 用户要求按"营收/交易量/用户数"三个口径切换 Treemap，模型为了让三个切换按钮"看起来对等"，在用户数缺失的项目上悄悄留空（那部分方块因为没有数值直接消失），没有做任何说明。

Reason: 缺失数据不该被悄悄留白，那样图表在读者眼里和"渲染坏了"没有区别，也不该为了凑对称而编造数值。覆盖率不齐的口径应该整个从切换控件里拿掉，换成图表外的说明或表格，并写清楚原因——"三个口径都做成切换按钮"看起来更工整，但工整不能建立在编数据或留空洞之上。
</bad-example>
