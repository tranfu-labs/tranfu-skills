# 会话修正沉淀

四步把会话中的纠正变成对应 SKILL 沉淀表（下称沉淀表）里的行，
用户纠正与现实纠正分表存放；核心防错是工作流第 2 步的资格门与归属路由。

## 工作流

1. 通读会话，列举两类纠正候选：用户的历次修正（含回退指令和
   “不对 / 不要 / 算了”类承接语），以及现实纠正——会话中遇到的
   报错 / 翻车与由此确立的正确做法。无任何候选 → 报告“无可沉淀项”并结束。
2. 每条先过资格门：是否存在一个被**否定**的既有行为？否定者分两类：
   - 用户纠正：agent 先有既有行为，被用户否定（偏好 / 约定类）；
   - 现实纠正：现实（报错、翻车、数据对不上）否定了原做法，门槛是
     根因已查明且正确做法已在会话内验证；正确做法尚未找到 →
     先去找（复现 / 查文档 / 调研），找到后与用户确认，确认通过才算过门；
   - 两类都不是——任务范围指令（如“只改这个文件”“只加两个节点”）、
     共同讨论后拍板的当次方案（用户在选项里选择，没有否定错误）、
     纯一次性修改（如“这个标题改一下”）→ 列入“一次性不沉淀”清单，到此为止。
   过门后再问归属：它在纠正哪个 skill 的行为？
   - 答得出具体 skill → 进步骤 3；
   - 答不出、属通用工作方式偏好 → 列入“归 memory”清单，NEVER 写进任何 SKILL；
   - 模糊或跨多个 skill → 回读会话上下文定位归属；仍定不了 → 问用户，
     不硬塞进最接近的 skill。
3. 按类落表，每条恰好一行。
   - 用户纠正 → 落点 SKILL 的用户修正沉淀表：场景（agent 当时做了什么）→
     期望输出（用户想要的内容）。落点没有该表但已有同构的场景对照表
     （输入/场景 → 输出）→ 直接追加进该表；两者都无 → 在文件末尾建带
     「用户修正沉淀」小节标题的两列 markdown 表（场景 | 期望输出）。
   - 现实纠正 → 落点 SKILL 的「现实纠正沉淀」三列表：触发场景 | 正确做法 |
     因果链。因果链列只放指向 `references/<slug>.md` 的链接，复盘写进该
     reference 文档（现象 → 根因链 → 关键证据 → 结论边界）；SKILL 文件
     一律不放因果链本体。无此表 → 在文件末尾建最小三列表。
   追加前检查冲突：新行与既有行矛盾 → 改写该旧行（最新纠正覆盖），
   并在对账单标注“覆盖”。落点 SKILL 文件不存在 →
   报告并问用户（不新建 skill，创建走创建流程）。
4. 产出对账单：每条纠正的「序号 → 落点 SKILL 路径 → 追加的表格行
   （现实纠正另附 reference 路径）」三元组，
   每行须可对回会话中的原始修正；“归 memory”与“一次性不沉淀”两份清单单列，
   前者标注“待归档”——是否写入 memory 由用户或运行时记忆机制决定，
   本 skill 不代写。结束。

## 编写规范

- 一条纠正恰好一行：用户纠正两列（场景 → 期望输出），现实纠正三列
  （触发场景 → 正确做法 → 因果链链接）。只记结论不记场景的规则下次无法命中。
- 表格行必须自足：只看这一行就能做对；reference 是出错或质疑时才回读的，
  非必要不读取。
- 只追加表格行：不新开章节、不复述 skill 已有内容、不借机重构或扩写。
  豁免仅三处（操作见工作流第 3 步）：新建最小表时可加小节标题；
  新纠正与既有行矛盾时改写该旧行（最新纠正覆盖）；
  现实纠正的因果链复盘落 `references/<slug>.md`。
- 抽象到可复用：剥离的是会话环境的项目名与文件路径；纠正对象本身的具体值
  （字体名、flag、数值）是期望输出的一部分，必须保留。

<example>
会话中用户说过“图标别用渐变，改纯色描边”（修正某图标生成 skill 的输出），
又说过“以后回答我都用中文”（通用偏好）。
输出：前者 → 该图标 skill 的用户修正沉淀表追加一行「用户指定图标风格 →
纯色描边，不用渐变」；后者 → 归 memory 清单，不碰任何 SKILL。
</example>

<example>
会话中批量签名测试卡顿 40 秒，查明根因是只签不发导致钱包反复轮询查不到的
交易、又撞上公共节点限流形成自锁，换网络后同规模降到 6 秒，正确做法已验证。
输出：对应测试 skill 的现实纠正沉淀表追加一行「只签不发的批量签名测量 →
在配额干净的网络上测，签名笔数最小化 → `references/wallet-pending-tx-selflock.md`」，
因果链复盘写进该 reference 文档。
</example>

<bad-example>
WRONG: 把“用户嫌方案过度设计”写进当次讨论的那个 skill，并顺手新开
“设计原则”章节展开三段说明。
Reason: 该修正针对 agent 通用工作方式，归 memory；新开章节还违反
“只追加表格行”——沉淀动作本身犯了只做加法的病。
</bad-example>
