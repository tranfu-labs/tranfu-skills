# 会话修正沉淀

四步把用户修正变成对应 SKILL 用户修正沉淀表（下称沉淀表）里的行；
核心防错是工作流第 2 步的路由过滤。

## 工作流

1. 通读会话，列举用户的历次修正（含回退指令和“不对 / 不要 / 算了”类承接语）。
   无任何修正 → 报告“无可沉淀项”并结束。
2. 每条修正过路由过滤：它在修正哪个 skill 的行为？
   - 答得出具体 skill → 进步骤 3；
   - 答不出、属通用工作方式偏好 → 列入“归 memory”清单，NEVER 写进任何 SKILL；
   - 答不出、只是一次性任务修正（如“这个标题改一下”）→ 列入“一次性不沉淀”清单；
   - 模糊或跨多个 skill → 回读会话上下文定位归属；仍定不了 → 问用户，
     不硬塞进最接近的 skill。
3. 每条提取一对——场景（agent 当时做了什么）→ 期望输出（用户想要的内容），
   以一行追加进落点 SKILL 的沉淀表。追加前检查冲突：新行与既有行矛盾 →
   改写该旧行（最新修正覆盖），并在对账单标注“覆盖”。
   落点没有沉淀表但已有同构的场景对照表
   （输入/场景 → 输出）→ 直接追加进该表；既无沉淀表也无同构场景表 →
   在文件末尾建带「用户修正沉淀」小节标题的两列 markdown 表（场景 | 期望输出）。
   落点 SKILL 文件不存在 →
   报告并问用户（不新建 skill，创建走创建流程）。
4. 产出对账单：每条修正的「序号 → 落点 SKILL 路径 → 追加的表格行」三元组，
   每行须可对回会话中的原始修正；“归 memory”与“一次性不沉淀”两份清单单列，
   前者标注“待归档”——是否写入 memory 由用户或运行时记忆机制决定，
   本 skill 不代写。结束。

## 编写规范

- 一条修正恰好一行两列：场景 → 期望输出。只记结论不记场景的规则下次无法命中。
- 只追加表格行：不新开章节、不复述 skill 已有内容、不借机重构或扩写。
  豁免仅两处（操作见工作流第 3 步）：新建最小表时可加「用户修正沉淀」小节标题；
  新修正与既有行矛盾时改写该旧行（最新修正覆盖）。
- 抽象到可复用：剥离的是会话环境的项目名与文件路径；修正对象本身的具体值
  （字体名、flag、数值）是期望输出的一部分，必须保留。

<example>
会话中用户说过“图标别用渐变，改纯色描边”（修正某图标生成 skill 的输出），
又说过“以后回答我都用中文”（通用偏好）。
输出：前者 → 该图标 skill 的沉淀表追加一行「用户指定图标风格 → 纯色描边，不用渐变」；
后者 → 归 memory 清单，不碰任何 SKILL。
</example>

<bad-example>
WRONG: 把“用户嫌方案过度设计”写进当次讨论的那个 skill，并顺手新开
“设计原则”章节展开三段说明。
Reason: 该修正针对 agent 通用工作方式，归 memory；新开章节还违反
“只追加表格行”——沉淀动作本身犯了只做加法的病。
</bad-example>
