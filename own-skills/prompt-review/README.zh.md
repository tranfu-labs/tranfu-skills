# prompt-review 提示词审查

围绕一个核心判断做工程审查：**这段内容承载的信息，模型能不能自己推断出来？** 能推断的是噪音（该删）；不能推断的，检查它的家是否唯一、形态是否匹配类型。审查是双向的——既补缺失的承重信息，也删堆积的冗余规则，绝不用"新开章节"来满足任何检查。

审查先按信息重心判定目标类型——**经验纠偏型**（场景→预期输出对照、真实数值）、**编排型**（多步流程、subagent 分工）、**工具封装型**（CLI/API 调用契约）、**参考型**（外部知识镜像）。每个类型只带一对检查：一条"必须满足"（该类型独有的价值载体）加一条"特征病"（该类型独有的腐败方式），叠加在一小组通用检查之上（路由面、触发覆盖、场景化排除、一个事实一个家、信息存在即满足、硬标记限定安全边界）。

产出结构化的 `REVIEW_PACKET`：每条问题带严重级别、修法分型、命中的检查名、全部位置（冗余问题合成一条批量问题列出多处）、证据和可观测的验收标准。有标准答案的（`direct`）直接给具体改法；依赖作者判断的（`think`）给 2–3 个决策性问题而不是编造答案。只审不改，从不写盘。

## 什么时候用

- 刚写完一个 skill / agent / prompt 文件，想要一次工程视角的批评
- skill 越写越重时，想找出冗余章节——被复述的规则、照抄场景表的验收表、重复正文的示例
- 审查存量提示词库：触发覆盖缺口、排除条件里指名兄弟 skill、过时的工具契约
- 完全离线——清单自包含，不需要网络

## 怎么触发

对 Claude 说：
- "帮我审一下这个 prompt：agents/evaluator.md"
- "review skill ~/.claude/skills/foo/SKILL.md"
- "检查这个 agent 定义的提示词质量"

或者直接粘贴一段提示词文本让它审。

## 你会得到什么

- 一个类型判定（四型之一，判不出则附一个反问给你）
- 一份结构化 `REVIEW_PACKET`，每条问题对应具名检查项，带严重级别和位置
- 冗余发现合成一条批量问题，指明每个事实唯一保留的家，而不是十几条零散挑剔
- `direct` 问题附可直接落盘的改法；`think` 问题附 2–3 个问题（问什么 / 为何只有你能答 / 答完落到哪）
- 本 skill 只审不改——要不要应用改法，由你或调用它的工作流决定。
