# 产品 UI 风险审查

## 目的

使用这个 skill 审查资产、账户、授权、签名确认、交易提交、跨系统流转等产品 UI 流程是否足够清楚、可信、可恢复，并且适合交给真实用户使用。重点关注用户点按钮前是否理解后果、关键状态是否完整、失败后是否能恢复、风险文案是否具体，以及高风险操作是否容易误触或重复提交。

默认工作权限是只审查：输出发现和建议，NEVER 编辑文件，除非用户明确要求修复、实现或改写。
如果用户意图在「审查」和「完善/修复」之间模糊，MUST 默认走审查模式，并在输出中说明没有改文件。

这个 skill 主要做两件事：

- 审查模式：找出资产型、授权型、交易型产品 UI 在上线前会伤害用户决策、操作安全或恢复路径的问题。
- 完善模式：当用户明确说「完善」「修复」「按产品 UI 要求补齐」「直接改」时，把审查发现落成 PRD、文案、交互状态或代码修改。

## 工作流

CREATE A TODO LIST FOR THE TASKS BELOW:

1. 识别审查目标。如果用户提供 PRD、设计稿、截图、代码库、路由或线上 URL，就以该材料为目标；如果没有目标，要求用户补充材料并停止。
2. 归类产品流程：资产查看、资产兑换、领取、支付、授权、签名确认、交易提交、转账、账号安全、开通/关闭服务、审批、数据导入/导出、跨系统流转、异步任务、批量操作，或其他高风险流程。
3. 提取用户决策路径。记录主要用户、目标动作、前置条件、涉及对象、金额/数量/范围、目标账户或目标系统、费用/耗时/限制，以及成功后果。未知项必须显式标记。
4. 为每一步归类动作风险：只读、表单提交、授权、签名确认、支付、交易提交、转账、批量变更、不可逆操作、跨系统流转，或长时间异步操作。
5. 按下方清单审查产品。优先处理可能造成用户损失、误操作、重复提交、不可逆误解、恢复路径中断或上线混乱的问题。
6. 使用可用材料验证证据。对于代码，检查相关文件；对于可运行应用或线上 URL，在工具可用时做浏览器验证；对于截图或 PRD，不要声称做过运行时验证。
7. 按用户意图路由输出。如果用户只要求审查，输出 `PRODUCT_UI_RISK_REVIEW_REPORT`，先列阻塞问题，再列改进建议、验证记录和未解决假设，然后结束。
8. 如果用户明确要求完善或修复，先按「强制完善规则」修改可编辑目标，再输出改动文件、已运行验证、未验证项和 `PRODUCT_UI_RISK_REVIEW_REPORT` 摘要，然后结束。

失败路径：

- 如果目标不可用或不可读，报告 blocker，说明缺失的材料并停止。
- 如果用户、对象、金额/数量、目标系统、权限或操作后果未知，默认带着明确假设继续；只有当缺失值会改变风险判断时，才问一个简短问题。
- 如果用户要求法律合规、安全漏洞、投资建议、财务收益判断或底层系统正确性结论，说明本 skill 只覆盖产品 UI 风险，并询问是否继续做 UI 风险范围内的审查。
- 如果无法真实操作关键流程，就做静态审查，并把真实交互验证列为未验证。
- 如果用户要求修复但没有提供可编辑源文件，返回审查结果，并说明需要哪些文件或材料才能打补丁。

## 强制完善规则

进入完善模式后，MUST 优先修复 `critical` 和 `high` 问题；只有在高风险问题已经处理或明确不可编辑时，才处理 `medium` 和 `low` 打磨项。

### 必须补齐的信息

- 任何资产、账户、支付、授权、签名确认、交易提交、转账、批量变更或跨系统流转按钮附近，MUST 显示对象、范围、金额/数量、目标、费用/耗时、权限变化和完成后果中的相关项。
- 按钮文案 MUST 具体。使用「支付 128 元」「授权访问客户名单」「确认兑换 100 USDC」「提交交易」「转出 2.5 ETH」「导出全部订单」这类动作文案，不用只有「Confirm」「Submit」「OK」「继续」的泛化文案。
- 如果数据未知、加载中、过期或读取失败，MUST 阻断高风险操作或清楚标注状态，NEVER 让用户基于不完整数据提交高风险动作。

### 必须补齐的状态

- 未满足前置条件：说明缺什么、为什么需要，以及满足后能做什么。
- 权限不足：说明缺少哪类权限，并给出申请、切换账号或联系管理员路径。
- 数据为空或不完整：说明当前能否继续；高风险操作必须被阻断或降级。
- 用户取消或拒绝：页面保持可恢复，并说明用户可以重试或返回。
- 操作处理中：阻止重复提交，说明正在等待系统确认或任务执行。
- 操作成功：说明结果，并提供下一步、详情页、记录或返回路径。
- 操作失败：说明可能原因，提供重试、修改输入、联系支持或查看详情路径。

### 授权、签名确认和交易提交

- 授权、签名确认和正式提交 MUST 拆成可理解的步骤，除非目标材料明确证明该流程只有一个低风险动作。
- 授权 MUST 说明授权对象、权限范围、有效期或撤销方式，以及为什么需要授权。
- 签名确认 MUST 说明用途、对象、影响范围和后果，NEVER 把签名描述成无风险动作，除非目标材料能证明它不产生授权、提交或资产变化后果。
- 不可逆或资产相关操作 MUST 在提交前展示对象、范围、后果和恢复可能性，NEVER 只靠颜色、图标或禁用态表达风险。
- 正式提交前 MUST 让用户看到会改变什么、影响谁、成本是多少、目标系统或目标账户是谁，以及提交后如何确认结果。

### 跨系统与异步恢复

- 跨系统流程 MUST 显示来源系统、目标系统、对象、预计耗时、失败恢复路径和结果确认入口。
- 如果结果依赖异步任务、队列、第三方系统或延迟同步，MUST 标注数据可能延迟，并提供刷新、任务详情或支持路径。
- 如果流程可能卡住、超时或部分成功，MUST 给用户一个判断和恢复入口。

### 修改边界

- MUST 只修改用户提供或任务范围内的 PRD、文案、设计说明或代码文件。
- NEVER 声称已经完成真实支付、真实授权、生产发布、底层安全或法律合规验证，除非实际运行并记录了对应验证。
- NEVER 输出投资建议、收益保证、法律合规结论或底层系统安全结论。

## 审查清单

### 产品匹配与用户决策

- 页面或流程说明用户能做什么、完成后会改变什么，以及需要哪些前置条件。
- 主操作足够具体：对象、范围、金额/数量、目标和后果要出现在操作附近。
- 关键假设在提交前可见，例如费用、耗时、限制、撤销能力、影响范围、审批条件或生效时间。
- 空状态、加载中、数据过期、数据不完整和数据不可用状态不会把用户带入危险操作。

### 权限、对象与范围

- 覆盖未登录、权限不足、角色不匹配、对象缺失、范围过大、目标不可用和数据变化状态。
- 当用户身份、权限、目标对象或操作范围影响决策时，它们必须在相关位置可见。
- 长名称、编号、账户、任务 ID、批量对象和关键数字要可识别；在有用时可复制，并且不会造成布局溢出。
- 不要暗示登录、授权或审批通过等于结果安全，除非流程真的证明了这些结果。

### 授权、签名确认与交易提交

- 授权、签名确认和正式提交必须在视觉和文案上区分开。
- 授权要说明对象、范围、有效期、撤销方式，以及为什么需要该权限。
- 签名确认要说明用途、对象、影响范围和后果，不要只写「请确认」。
- 提交确认步骤要展示会改变什么、影响谁、成本是多少、目标系统或账户是什么，以及下一步会发生什么。
- 处理中、成功、失败、超时、部分成功、重试和查看详情状态必须可恢复。
- 高风险流程要阻止重复提交，并在可能时提供清楚的取消或恢复路径。

### 跨系统与异步流程

- 跨系统流程要说明来源、目标、对象、预计时间、费用/限制，以及失败/恢复路径。
- 多步骤流程要展示进度，并且不能隐藏下一步需要用户做什么。
- 异步任务或延迟同步要明确标注，避免用户把过期数据误解为丢失或操作失败。

### 信任、文案与减害

- 风险文案必须针对具体动作，不写空泛的 caution。
- 禁用态控件要在控件附近说明阻塞原因。
- 产品不能暗示收益保证、绝对安全、合规通过或无风险。
- 新手文案只在影响决策时解释概念；专家流程仍应保持可扫读。

### 上线准备度

- 在相关场景下覆盖 happy path、空状态、加载中、错误、未满足前置条件、权限不足、数据不完整、用户取消、处理中、成功和失败。
- 移动端和桌面端都要保证决策关键信息、数字、按钮和警示文案可读且不被遮挡。
- 当用户需要操作后的确认或恢复时，提供详情页、记录、帮助文档、客服/支持或 fallback 路径。
- 产品要有清楚的上线阻塞规则：可能造成资金损失、权限误授、资产误操作、数据误删、批量误操作或不可逆误解的问题都属于 blocker。

## 输出格式

审查类任务输出：

```yaml
PRODUCT_UI_RISK_REVIEW_REPORT:
  target:
    artifact: <prd|design|screenshot|code|route|live-url|unknown>
    product_surface: <产品流程分类>
    primary_user: <值或 unknown>
    core_action: <值或 unknown>
    risk_level: <low|medium|high|critical|unknown>
  blocking_issues:
    - id: B1
      severity: critical|high
      area: <decision|permission|object|confirmation|submission|async|copy|layout|support>
      evidence: <来自目标材料的具体观察>
      user_risk: <用户可能遭遇的问题>
      recommended_fix: <具体下一步>
  improvements:
    - id: I1
      severity: medium|low
      area: <area>
      evidence: <具体观察>
      recommended_fix: <具体下一步>
  verification:
    checked:
      - <实际检查过的材料、文件、视口、状态或流程>
    unverified:
      - <未检查的交互、权限、数据条件、视口或真实环境>
  assumptions:
    - <明确假设或 none>
  launch_readiness: block|conditional|pass|unknown
```

实现或修复类任务输出：

```yaml
PRODUCT_UI_RISK_FIX_SUMMARY:
  changed_files:
    - <被修改的文件或 none>
  fixed_blockers:
    - <已修复的 critical/high 问题>
  remaining_risks:
    - <仍未解决或无法编辑的问题>
  verification:
    checked:
      - <实际运行的检查>
    unverified:
      - <未验证的交互、权限、数据条件、视口或真实环境>
```

然后附上同样的 `PRODUCT_UI_RISK_REVIEW_REPORT` 摘要。

## 严重级别

- `critical`：可能造成资金损失、权限误授、资产误操作、数据误删、批量误操作、敏感信息泄露、不可逆误解，或高风险动作后的恢复路径中断。
- `high`：可能导致提交失败、重复提交、核心状态缺失、风险文案误导，或影响上线的移动端/可读性问题。
- `medium`：产品理解成本高、边界状态不完整、恢复路径弱、文案不清，或非阻塞布局问题。
- `low`：不明显改变用户风险的打磨、术语、层级或一致性问题。

## 示例

<example>
用户说：「按产品 UI 要求帮我完善这个资产兑换页面。」

处理：先识别页面缺失的资产、金额、目标账户、授权、签名确认、交易提交、处理中、失败和成功状态；如果有可编辑代码，补齐具体按钮文案、授权独立步骤、提交确认、防重复提交、失败恢复入口和交易结果详情；最后输出 `PRODUCT_UI_RISK_FIX_SUMMARY` 和上线准备度摘要。
</example>

<example>
用户说：「帮我审查这个支付流程，准备上线。」

处理：把产品流程归类为支付；检查金额、收款方、费用、支付方式、失败原因、处理中、防重复提交、成功回执和退款/客服路径。最后输出 `PRODUCT_UI_RISK_REVIEW_REPORT`，并把上线阻塞项放在最前面。
</example>

<example>
用户说：「帮我审查这份跨系统导入 PRD 的产品风险。」

处理：把产品流程归类为跨系统流转；提取来源系统、目标系统、对象、预计耗时、失败恢复路径和任务详情入口。如果 PRD 缺少部分成功、延迟同步或失败重试状态，把它们标成高风险发现。
</example>

<bad-example>
WRONG: 「按钮旁边有红色图标，所以用户会知道风险。」

Reason: 高风险 UI 必须用具体文案说明风险、对象、范围和后果，不能只靠颜色或图标表达。
</bad-example>

<bad-example>
WRONG: 「提交和授权可以合成一个按钮，因为弹窗会展示细节。」

Reason: 授权和正式提交是两个不同的用户决策。产品必须在弹窗或系统确认出现前分别解释每一步。
</bad-example>
